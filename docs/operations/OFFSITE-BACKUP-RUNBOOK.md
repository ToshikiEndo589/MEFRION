# 独立バックアップと復旧

2026-10-23実装。Supabase本番とは別の、既存Sitesに接続した非公開R2領域へ保存。
本番のMac・元プロジェクトが停止しても、保存先と復旧キーから取り出せる。
新しい有料プラン・外部契約は追加していない。

## 自動処理

本番の `mefrion-offsite-backup` Cronが毎分、処理の有無を確認する。
新しいDBスナップショットは前回から24時間後に取得し、Edge実行1回につき最大4件ずつ
写真・動画を転送する。中断時は3分のリース期限後に再開、失敗時は5分待って再試行する。
同一のStorageメタデータ版は重複転送しない。

DB・Authの52テーブルとStorageの管理情報を1つのSQL文で取得し、DB内でPGP暗号化する。
転送前にDBスナップショット、メディア、目録をそれぞれAES-256-GCMで暗号化する。
保存先には復号鍵を置かない。各ファイルを読み戻してSHA256を照合し、全ファイルの
存在確認を終えた時だけ暗号化目録を発行してバックアップ完了とする。

対象は家族アルバム原本、公開派生画像、動画とポスター、アプリの行データとAuthユーザー・
ID・MFA情報。参考素材と検索特徴量は再取り込みできるため、日次のメディア転送から除外。
セッション/リフレッシュトークン、プロジェクト秘密鍵、外部SMTP/OAuthの資格情報は復元しない。

削除・退会後も、既に取ったコピーには最大7日残る。期限を過ぎた目録・DBコピーを削除し、
保持中の目録から参照されなくなったメディア版も削除する。別の合成データで期限切れの
暗号化ファイル3件を作り、自動消去まで確認した。

## 復旧キー

Mac内の `.local/MEFRION-production-recovery-kit.json` は所有者だけが読める0600。
保存先アクセスキー、AES鍵、PGPパスフレーズ、確認済みバックアップID、暗号化した
バックエンドソースの取り出し先が入っている。チャット・Git・公開Siteへ掲載しない。
**運営者はこのファイルをMacとは別の安全な保管場所にも保存すること。**
これを失うと、保存先にデータが残っていても復号できない。

## 復元訓練

配備時の復元ツールは `scripts/verify_offsite_backup.py`。
既定で認証済みの独立保存先目録から最新バックアップを選ぶため、元のSupabaseへの
問い合わせは不要。取得にはcurlの標準TLS検証を使い、キーは引数に載せない。

```
.venv/bin/python scripts/verify_offsite_backup.py
```

AES-GCMの改ざん検出、PGPのローカル復号、全メディアのSHA256とサイズを確認する。
DB行は開発プロジェクトのTEMPテーブルに復元して件数を照合し、必ずROLLBACKする。
メディアは開発の一時非公開バケットへ復元・再取得して照合後、試験用バケットを撤去。
利用者のアルバム、本番データ、既存の開発データを上書きしない。

実測: 52テーブル141行、写真/ポスター4件と動画2件、合計6ファイルを復元。
本番への読書き0回で成功。`docs/evidence/OFFSITE-RESTORE-20261023.json` を参照。

## 障害時の本復旧

1. 復旧キーを安全な環境へ用意し、暗号化されたバックエンドソースと最新目録を取り出す。
2. 独立した復旧先を用意し、同梱SQL移行とEdge Functionsを適用する。顧客アクセスは閉じておく。
3. メディアをStorage APIから戻し、DB行を制約・依存順・Auth整合性を確認して戻す。
   `storage.objects` の行を直接書き戻して、ファイルがあるように見せかけない。
4. 退会・削除の台帳を適用し、古いスナップショットから退会者や停止投稿を再公開しない。
5. SMTP/OAuth/内部ワーカー鍵を再設定し、以前のログインセッションは失効させる。
6. 認証・家族権限・非公開画像・投稿・削除の通し確認後に、アプリの接続先を切り替える。

今回の復元試験は隔離テーブルと一時バケットへのデータ復元であり、新しい本番プロジェクト
への全面切替訓練やPITRではない。RPOは日次、転送待ちや障害中は直近成功時点まで戻る。
JSONスナップショットは非圧縮8MiB、メディアは1件50MiB以内。容量超過・失敗・古い最終成功は
運営コンソールの `offsite-backup` と非公開キューで監視する。規模拡大時は上限と転送量を見直す。

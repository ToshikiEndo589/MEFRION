# ホーム表示・操作の追加高速化（2026-10-13）

対象は既存のiPhone Debug版クラウドSNS。公開・家族写真の権限、公開終了、ブロックを優先し、公開写真は引き続き no-store のゲートウェイ経由で取得する。ディスクに公開写真を保存しない。

## 実装

- いいね・保存・フォロー成功後に投稿一覧RPCと写真全件を再取得していた処理を廃止。サーバーが成功を返した後、対象の投稿状態と件数のみ更新する。コメント一覧を再取得した時は表示中の投稿件数に反映する。
- 保存済みログイン復元中、認証が確定した時点でホームの投稿取得を開始し、Pet一覧取得と並行させる。重複する初回フィード取得は抑止する。
- 公開写真の先頭1枚を60ms先行して取得し、その後は最大6件のスライド窓で取得する。遅い1枚が次の6枚を止めない。ImageIOでJPEGをUI actor外で復号する。
- 最初に取得する写真をページ先頭12投稿のカバーに絞り、残りの投稿とカルーセル写真は画面に入った時に取得する。復号済み写真のメモリ保持は画面上の写真を守りながら原則24枚に制限し、戻った時はゲートウェイで再確認して取得する。公開終了後の画像は投稿一覧の再検証で削除し、表示中でないIDの取得結果も破棄する。
- 投稿が既に表示されている時は、別操作の `busy` 表示でホーム上部を押し下げない。

## 実測・検証

- 開発Supabaseの承認済み一時公開20投稿で匿名feed RPCを測定：20件、0.163秒。写真先頭1枚は53,639バイト、0.406秒。続く6枚の並列取得は各0.374〜0.518秒。これはMacからの通信単体で、iPhone画面表示時間や改善前後の同条件比較ではない。
- 最終の画像24枚制限・画面出現時取得のコードでSimulator Debugビルド成功。公開写真の表示、全幅レイアウト、認証導線、タブ切替のUIテスト2件成功、失敗0（`/tmp/mefrion-feed-cache-final.xcresult`）。一時UI許可マーカーは実行後に削除した。
- 画像24枚制限を入れる前の単体39件成功、失敗・skip0（`/tmp/mefrion-feed-unit-final.xcresult`）。制限を入れた後の単体再実行はXcodeのテストログ終了待ちで停止し、中断した。制限追加後のSimulator Debugビルドは再成功。最終の重複画像要求抑止の小変更後もビルド成功し、公開写真を開くUIテスト1件が成功（`/tmp/mefrion-feed-last-check.xcresult`）。
- 途中の5タブUI試験1件は必要な `home-navigation-fixture.json` がなく開始前に失敗した。機能動作の失敗ではないが、成功に含めない。
- XCTestの `app.launch()` から最初の画像検出までは10.06秒だった。アクティビティ記録上、automation session確立とアプリidle待ちが大半を占めるため、利用者がiPhoneで待つ時間とはみなせない。実機 iPhone (59) は今回 unavailable で、更新・体感速度計測は未実施。

## 残る検証

実機での冷起動・復帰・長時間スクロール・低速回線・通信断・メモリ圧迫、同時多数ユーザー時のサーバー性能を測る必要がある。Instagram同等のUX到達はまだ実証していない。公開終了・権限変更時の即時確認を保つため、公開画像の永続キャッシュや無検証CDN配信は採用していない。
